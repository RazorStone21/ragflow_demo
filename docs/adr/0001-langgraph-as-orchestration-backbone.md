# ADR-0001：以 LangGraph 1.x 作为唯一编排主干

## 背景

平台要同时交付多类长流程智能体（政务政策问答、工业巡检、工单处置等），这些流程具备共同特征：

- **有状态、可中断、可恢复**：一次运行可能跨小时甚至跨天（等待人工审批、等待数据补齐），需要"中断—持久化—恢复"；
- **需人机协同（HITL）**：高危动作必须停在人工确认点，且确认后从断点继续，而不是从头重跑；
- **需可观测与可回放**：事故复盘、合规审计要求能完整回放某次运行的节点轨迹；
- **需多智能体协作**：复杂业务要拆成子域子图，由中心调度器编排；
- **需私有化部署**：面向能源/工业客户私有化交付，运行时不依赖外部 SaaS。

在选型时，团队同时评估了"用框架编排"与"用可视化画布编排"两条路线。画布路线（Dify / FastGPT / RAGFlow 的 Agent 画布）上手快，但把核心业务流程落在画布上会带来三个不可接受的问题：流程定义难以进入 Git 做代码评审与差异对比；状态模型与中断语义受画布实现约束，无法自建持久化检查点；许可证层面存在对外多租户运营的限制（见"合规与许可证"）。

## 决策

**锁定 LangGraph 1.x 作为平台唯一的核心业务编排主干**，并遵守以下不可协商的边界：

1. **代码即图**：编排逻辑只以 Python 代码形式存在于 `src/agent_platform/agents/<name>/`，进入 Git、走 Pull Request、跑全套门禁（ruff → mypy → pytest → 评估）；
2. **状态即契约**：每个智能体在 `state.py` 中定义唯一 State Schema，聚合字段显式声明 reducer；
3. **持久化检查点**：有状态、长流程、需 HITL 的图编译时**必须**挂载 `langgraph-checkpoint-postgres`（`PostgresSaver` / `PostgresStore`）；内存实现仅允许用于单元测试；
4. **HITL 用原生机制**：必须用 `interrupt()` + `Command(resume=...)` 实现中断与恢复，禁止用自建标志位 + 轮询模拟；
5. **子图分层**：复杂流程用 Subgraph 分层封装；多智能体默认用 `langgraph-supervisor`，去中心化交接（swarm）需另行说明理由；
6. **其他系统只做"能力提供方"**：可视化平台（Dify / FastGPT / RAGFlow 画布）**不得**承载核心业务流程编排，它们只能作为知识后端、工具服务或对照参考。

## 备选方案与权衡

| 方案 | 优势 | 为什么未采用 |
|---|---|---|
| **LangGraph 1.x**（选定） | 代码即图，可评审可测试；原生检查点与 `interrupt()`；官方持续测试的部署目标是 Kubernetes；库为 MIT 可自由私有化 | — |
| AutoGen | 多智能体对话模型成熟，研究社区活跃 | 编排以"对话轮次"为中心，长流程的状态与恢复语义不如显式状态图清晰；难以表达"确定性路由 + 人工审批点"这类强约束流程；生态与 LangChain/LangGraph 工具链重叠但不同源，维护两套成本高 |
| CrewAI | 上手快，角色抽象直观 | 抽象层次偏高、控制粒度粗；状态持久化与中断恢复能力弱于需求；复杂分支流程需要绕开框架实现，等于自建编排 |
| Dify / FastGPT 画布 | 可视化、交付演示快 | 流程定义不在 Git，无法代码评审与原子化重构；状态模型受限于平台；许可证为"修改版 Apache-2.0 / source-available"，对外多租户运营受限（NO-13） |
| RAGFlow 画布 | 与知识后端同栈，检索演示方便 | 同上（流程不在 Git、状态受限）；且其强项是文档工程而非编排，用它编排等于放弃检索能力的自主演进 |
| 自研状态机 | 完全可控，无第三方依赖 | 需自行实现检查点、序列化版本兼容、中断恢复、流式事件、追踪集成——这些正是 LangGraph 已被验证的部分，自研是重复投入且风险更高 |

## 后果

### 正面

- 流程定义可评审、可测试、可 diff、可回滚；每个节点可单独跑单元测试（注入 fake 依赖）；
- 检查点带来断点续跑、时间旅行（time-travel）与事故回放能力，直接满足审计要求；
- 状态契约显式化后，"节点不 mutate 入参""聚合字段声明 reducer"等约束可由测试与静态检查守住；
- 多智能体通过 Subgraph 与 supervisor 组合，无需引入第二套协作框架。

### 负面 / 需承担的代价

- **学习曲线**：团队需要理解 reducer、检查点、中断恢复、`stream_mode` 等概念，产出速度前期低于画布方案；
- **样板代码**：每个智能体需要 `state.py` / `nodes/` / `edges.py` / `graph.py` 的标准结构，简单场景显得重；
- **版本耦合**：LangGraph 1.x 的 API 演进（如序列化白名单、节点参数注入规则）需要跟随；升级前必须验证历史检查点可恢复（见 `CLAUDE.md` 9.3）；
- **越权使用的诱惑**：业务方可能仍要求"再挂一个画布做快速试错"。规范已明确禁止其承载核心编排，试错也必须回到代码路线。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 检查点序列化兼容性（升级后旧状态不可恢复） | 升级前跑"历史检查点可恢复"集成测试；序列化白名单显式声明，不用默认宽松模式跑生产 |
| 单图膨胀为"上帝图" | 节点文件 ≤ ~150 行；复杂流程拆 Subgraph；路由集中在 `edges.py` 的纯函数 |
| 框架自身缺陷或停更 | 库为 MIT，可从源码自行维护；编排逻辑（State/边/节点）是与框架解耦的资产，迁移成本可控 |

## 合规与许可证

- **LangGraph 库**：MIT，可自由私有化、可修改、可离线部署，无对外服务传染性；
- **LangGraph Platform**：商业许可。**离线 Self-Hosted Enterprise 需采购授权，不得绕过授权使用**。本平台的部署形态为"库 + 自建 api-server/worker + Kubernetes"，不依赖也不假定 Platform 能力（见 `CLAUDE.md` 第 11 章）；
- 依赖引入前已按 `CLAUDE.md` 10.6 核对许可证，未触碰 AGPL / source-available 红线。

## 迁移与回滚

- **引入**：`langgraph>=1.2.15,<1.3`（`uv.lock` 锁定）；经 `pyproject.toml` 声明，纳入常规依赖审查。
- **回滚**：若需替换编排框架，属于**架构级破坏性变更**，必须：① 新增 supersede ADR；② 提供 State/检查点数据迁移方案（历史检查点不可丢弃，否则在跑流程会中断）；③ 评估已交付智能体的存量改造量。当前无回滚计划。
