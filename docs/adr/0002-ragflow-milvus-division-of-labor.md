# ADR-0002：RAGFlow 与 Milvus 的双后端分工（文档工程 / 检索主链路）

| 项 | 值 |
|---|---|
| 状态 | Accepted（生效中） |
| 决策日期 | 2026-10-15 |
| 决策者 | 平台架构组（需求方确认：检索链路自持、向量库锁定 Milvus） |
| 关联 | [CLAUDE.md](../../CLAUDE.md) 第 7 章、NO-01、NO-19；[ADR-0001](0001-langgraph-as-orchestration-backbone.md) |
| 后续状态 | 不可就地修改；如需推翻（例如上游 RAGFlow 支持外部 Milvus），新增 supersede ADR 并指向本篇 |

## 背景

业务需求为"用 RAGFlow 构建 RAG 项目，向量数据库选型 **Milvus**"。即：期望同时得到 RAGFlow 的文档工程能力（多格式解析、扫描件 OCR、版面识别、切分、文档生命周期管理）与 Milvus 的向量检索能力（独立可扩、可备份、可控的索引与过滤策略）。

**核实结论（2026-10-15 当日核对上游仓库与官方 issue）**：RAGFlow 最新稳定版 **v0.27.2 不支持接入外部 Milvus**。其 `DOC_ENGINE` 仅接受 `elasticsearch` / `infinity` / `oceanbase` / `opensearch` / `seekdb` / `gaussdb`，官方明确拒绝"外部 Milvus 作为 DOC_ENGINE"的诉求（对应上游 issue #7749）。也就是说，**"RAGFlow + 外部 Milvus 一体化"在 v0.27.2 上不存在受支持路径**，只能二选一：要么放弃 Milvus 用 RAGFlow 自带引擎，要么让 RAGFlow 只承担它能做的事、把检索主链路自建在 Milvus 上。

补充事实：RAGFlow 的 `infinity` 引擎为进程内嵌、免部署外部 ES，在 16GB 内存的单机演示环境上更可行；而 Milvus 2.6 已是团队锁定的向量库（`CLAUDE.md` 技术栈表）。

## 决策

采用**双后端分工**，两个后端各自承担它最擅长且不可替代的部分，通过本平台的 `knowledge/` 层连接：

```
 源文档 ──► RAGFlow（文档工程后端，DOC_ENGINE=infinity）
              │  解析 / OCR / 版面识别 / 切分 / 文档生命周期
              │  REST: 数据集、上传、解析、chunks 分页
              ▼
        knowledge/ （自建同步与检索层，本平台代码）
              │  ① 同步：拉取 chunks → 归一化 → 内容指纹 → 嵌入 → upsert
              │  ② 检索：稠密 + BM25 混合检索 → 阈值过滤 → 重排 → 证据（带引用）
              ▼
        Milvus 2.6（索引与检索主链路）
              稠密向量 + BM25 稀疏向量 + 租户/数据集标量过滤
```

**职责边界（不可互相越界）**：

| 能力 | 归属 | 说明 |
|---|---|---|
| 文档解析、扫描件 OCR、版面/表格识别、切分 | **RAGFlow** | 这是选 RAGFlow 的理由；自研成本高、质量难保证 |
| 文档上传、解析状态、chunk 生命周期、文档管理 UI | **RAGFlow** | 沿用其成熟能力，不重复造 |
| 向量索引与检索（稠密 + 关键词混合） | **Milvus** | 生产可独立扩容、可备份；索引算法与参数由我方掌握 |
| 重排、阈值判定、证据构造与引用（来源/章节/页码/链接） | **本平台 `knowledge/`** | 检索质量策略必须在我们自己的代码里可评审、可回归 |
| 租户隔离与权限过滤 | **本平台 `knowledge/`** | 过滤表达式由 `milvus_schema.tenant_filter` 构造，调用方**无法绕过**（NO-19）；不依赖外部平台的多租户实现 |
| 业务编排与决策 | **LangGraph** | RAGFlow / Dify 画布**不得**承载核心业务流程（NO-01 / ADR-0001） |
| 嵌入与重排模型 | 经 **LiteLLM 网关**（逻辑名 `embedding` / `rerank`） | 演示期指向云端 API；上线切换私有化仅改网关映射，业务代码零改动（NO-02） |

**同步管线的幂等契约**：以"源文件路径 + 内容指纹（sha256）"为幂等键；Milvus 主键直接沿用 RAGFlow 的 `chunk_id`（`auto_id=False`），因此同一 chunk 重复入库是 upsert 覆盖而非新增，重复执行同步**不产生重复数据**。

## 备选方案与权衡

| 方案 | 优势 | 为什么未采用 |
|---|---|---|
| **双后端分工**（选定） | 同时拿到 RAGFlow 的解析质量与 Milvus 的检索可控性；检索策略、租户过滤、引用构造全部在我方代码内，可测试可回归；上游版本升级互不阻塞 | 代价是需要自建同步与检索层（`knowledge/`），并接受"两个后端都要运维" |
| A. 全用 RAGFlow（自带 DOC_ENGINE） | 单一系统、开箱即用、链路最短 | 与"向量库选型为 Milvus"的硬需求冲突；检索参数与过滤策略受平台实现约束，租户隔离无法在我方代码内强制校验；**且其画布容易诱导业务把编排搬进去，触碰 NO-01** |
| B. 全用 Milvus，自研 LlamaIndex 解析管线 | 技术栈统一，无外部平台 | 放弃 RAGFlow 的核心价值：中文政务文档的版面/表格/扫描件解析与 OCR 质量需要长期投入才能追平；在 10~20 份文档的演示范围外，长期维护成本高 |
| C. Fork RAGFlow，自行补齐 Milvus 连接器 | 表面上"两全" | 需长期维护上游合入补丁，升级即冲突；上游已明确拒绝该方向，等于背负一条永久分叉；许可证与商用条款亦需重新评估（NO-13） |
| D. 用 ES / Infinity 承载生产检索 | RAGFlow 原生支持、零适配 | 与 Milvus 选型冲突；且 ES 在 16GB 单机演示环境内存开销过大 |

## 后果

### 正面

- 检索质量策略（切分、Top-K、阈值、rerank、混合权重）全部落在 `src/agent_platform/knowledge/` 内，可按 `CLAUDE.md` 9.2 跑评估回归，改一处即可评测对比；
- 租户过滤在**我方代码**内强制构造，越权检索不依赖第三方平台的正确性（NO-19 的纵深防线）；
- 引用信息（文档名、页码、来源 URI）由我方在同步时抽取落库，答案的"证据绑定"不受上游 API 变化影响；
- 两个后端可独立升级、独立替换：RAGFlow 换版本不影响检索，Milvus 换集群不影响文档工程。

### 负面 / 需承担的代价

- **运维两套有状态系统**：RAGFlow（应用 + Infinity）与 Milvus（etcd + MinIO + standalone），单机演示环境需注意内存水位（16GB 场景下先入库、后按需停止 RAGFlow）；
- **同步管线是新增故障面**：解析完成 → 拉取 chunks → 嵌入 → upsert 之间存在窗口期，需幂等键与重跑能力来收敛（已由 `chunk_id` + 内容指纹保证）；
- **两处元数据可能漂移**：RAGFlow 侧文档被删除/重新解析后，Milvus 侧需相应清理（`delete_by_document`）；
- **比方案 A 多写代码**：`knowledge/` 层的同步与检索是必须自行维护的资产。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 上游 RAGFlow 未来支持外部 Milvus，本方案显得多余 | 分工边界清晰，届时新增 supersede ADR；迁移成本限于 `knowledge/` 的同步与检索实现，智能体与 API 层不受影响 |
| 上游客流/接口变更（chunk 分页、解析状态字段） | RAGFlow 客户端封装在 `knowledge/ragflow_client.py`，变更收敛于单文件；接口适配有单元测试（`httpx.MockTransport`） |
| 嵌入维度与 Milvus 集合维度不一致 | `MILVUS_DIM` 可配置；入库维度不符时 **fail-fast 报错**，不做静默截断 |
| 中文 BM25 分词效果不及预期 | 可先用 `standard` 分词或预分词回退；切分/分词策略变更属检索质量变更，必须跑评估回归（CLAUDE.md 9.2） |
| 云端嵌入/重排 API 在私有化交付中不可用 | 演示期用云端 API 快速验证；逻辑名映射隔离，切换私有化 Qwen3 系列仅改网关配置（NO-02） |

## 合规与许可证

- **RAGFlow**：Apache-2.0（含附加条款）。本项目**只用其文档工程能力**，不用其画布承载编排，不作为对外多租户运营底座——规避其附加条款的限制面（NO-13）；
- **Milvus 2.6**：Apache-2.0，可私有化、可改造；
- **LiteLLM**：MIT（代理层）；
- **云端嵌入/重排**：仅用于**演示阶段**。含客户文档内容出域到第三方 API 的合规风险，**上线前必须切换为私有化模型**（Qwen3-Embedding / Qwen3-Reranker 本地权重，权重许可证单独确认）；
- 演示语料为公开政务文件，不含客户数据与个人隐私。

## 迁移与回滚

- **引入**：RAGFlow 以官方 compose 形式独立部署（`DOC_ENGINE=infinity`，CPU 模式），与主 `docker-compose.yml` 通过共享网络互联；Milvus standalone 由本仓 compose 管理。
- **回滚**：
  - 若需回到"全 RAGFlow"（方案 A）：检索调用点集中在 `knowledge/retriever.py`，替换为 RAGFlow 检索 API 即可，智能体与 API 层不变；代价是放弃 Milvus 侧的混合检索与租户过滤能力；
  - 若需改为"全自研解析"（方案 B）：RAGFlow 客户端替换为解析管线，chunk 契约（`ChunkRecord`）保持不变，同步与检索层无需重写；
  - 两条回滚路径都**不需要**改动 `agents/` 与 `api/`，这是本分工设计的主要收益。

## 未决与后续事项（诚实记录）

- 上游 RAGFlow 的 `DOC_ENGINE` 支持矩阵随版本演进，本决策基于 **2026-10-15** 核实的状态（v0.27.2）；投标或上线前须按 `CLAUDE.md` 14.5 当日复核；
- 上线前必须完成私有化嵌入/重排替换与合规确认；
- LiteLLM 对上游 rerank 接口的透传能力在实现阶段以 spike 实测为准；若不支持，重排客户端在同接口约束下直连，并在 CHANGELOG 中记录该临时偏离。
